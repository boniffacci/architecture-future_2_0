# Обоснование событийного подхода

## Преимущества перед текущей архитектурой (Camel + DWH)

### 1. Гибкость и слабая связанность
- Домены развиваются независимо  
- Новые подписчики добавляются без изменения источников  
- Упрощается добавление новых бизнес-направлений  

### 2. Масштабируемость
- Горизонтальное масштабирование обработчиков событий  
- Возможность геораспределённого развёртывания  
- Обработка сотен терабайт в near-real-time режиме  

### 3. Повышение производительности
- Формирование отчётов за секунды вместо часов  
- Параллельная обработка потоков данных  
- Кэширование данных в витринах  

### 4. Надёжность и отказоустойчивость
- Механизмы повторной обработки (retry, DLQ)  
- Гарантированная доставка сообщений  
- Резервирование через репликацию событий  

### 5. Соответствие требованиям
- Разделение медицинских и аналитических данных  
- Контроль доступа на уровне событий  
- Аудит всех изменений через event sourcing  

### 6. Time-to-market
- Быстрое подключение новых источников данных  
- Гибкие трансформации в потоковом режиме  
- Самообслуживание для бизнес-пользователей

## Сравнение с текущим решением

| Аспект | Текущая система (Camel + DWH) | Целевая система (Event Platform) |
|------|-------------------------------|----------------------------------|
| Связанность | Жёсткая (точка-точка) | Слабая (через события) |
| Масштабирование | Вертикальное (дорого) | Горизонтальное (эффективно) |
| Производительность отчётов | Часы | Секунды / минуты |
| Time-to-market | Месяцы | Недели |
| Надёжность | Единая точка отказа | Распределённая отказоустойчивость |
| Гибкость | Требует изменений DWH | Независимое развитие доменов |
